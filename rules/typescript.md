# TypeScript Conventions
# ~/.claude/rules/typescript.md

## Module System

- ESM only — `"type": "module"` in package.json, no CommonJS
- Use `.ts` extensions in source, `.js` in compiled output
- `strict: true` in tsconfig.json — no exceptions
- Target: ES2024+ (Node.js 24+ APIs available)

## Style

- Prefer `type` over `interface` for data shapes (types compose better)
- Use `interface` only for class contracts or when extending is needed
- Explicit return types on exported functions
- Use `const` assertions for literal types: `as const`
- Prefer `unknown` over `any` — narrow with type guards

## ORM Patterns (example: Drizzle)

If your project uses a TypeScript ORM, these conventions (illustrated with Drizzle) translate to most query-builder ORMs:

- Schema definitions in `src/schema.ts` — single source of truth
- Migrations in a dedicated dir (e.g. `drizzle/`) — generated by the ORM's migration tool
- Always use the query builder, not raw SQL (except for complex scoring/CTE queries)
- Connection through `src/db.ts` — auto-detects remote and enables SSL
- Use transactions for multi-step mutations: `db.transaction(async (tx) => { ... })`

## MCP Server Patterns

- Tool definitions: use `@modelcontextprotocol/sdk` types
- Input validation: Zod schemas matching tool parameter definitions
- Error handling: return structured error responses, never throw unhandled
- Logging: stderr only (stdout is the MCP transport)
- Config: `src/config.ts` for all constants (scoring weights, thresholds, paths)

## Testing

- Vitest for unit tests, pytest for Python scripts in the same repo
- Integration tests against a real database (run sequentially to avoid pool exhaustion)
- `npx vitest run --exclude 'tests/integration/**'` for unit tests only

## Never

- `require()` or `module.exports`
- `any` type without a comment explaining why
- Console.log in production code (use stderr for MCP servers)
- Hardcoded connection strings — use environment variables via dotenv
